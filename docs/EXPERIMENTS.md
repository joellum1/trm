# Experiment log: transferring TRM to objective-conditioned mazes

This log records, for every experiment in the thesis, why it was run, how it
was set up, what it found and what it does and does not show. Numbers quoted
here come from `report/` (built by `python scripts/make_report.py` from the raw
outputs in `results/`); where the two ever disagree, `report/` is authoritative
because it is regenerated from data. Table and figure files are named in each
section; `report/README.md` lists all of them with their status.

**Research question.** Can a Tiny Recursive Model (TRM) pretrained on
Maze-Hard shortest-path solving be adapted to mazes with additional
objectives (mandatory checkpoints, optional reward and penalty tiles), and how
should success on such tasks be measured?

## Summary

|---|---|---|---|
| E1 | Does the published Maze-Hard checkpoint reproduce in our pipeline? | done | 85.2% exact (95% CI 82.9–87.3%), matching the published 85.3% |

| E5 | How much does exact match under- or over-state Maze-Hard performance? | done | 43% of the baseline's failures are correct alternative shortest routes; 91.6% valid-and-shortest |

Three measurement problems were found along the way and are documented in
[Measurement corrections](#measurement-corrections); two of them change
numbers or claims made before this log (Thesis B).

## Shared setup

**Model.** TRM, attention variant, about 7M parameters: H_cycles 3,
L_cycles 4, two transformer layers, hidden size 512, 8 heads, 16 puzzle
embedding positions, adaptive computation (ACT) up to 16 steps, bfloat16,
weights averaged with an exponential moving average (EMA, rate 0.999), which
is what is evaluated. Pretrained weights: `alphaXiv/trm-model-maze`,
`maze_hard_step_32550`. Resolved configs are in `config/resolved/`.

**Maze-Hard.** 30×30 mazes from `sapientinc/maze-30x30-hard-1k`; 1,000 test
mazes. Tokens `# SGo` (wall, empty, start, goal, path).

**Custom objective mazes.** Generated by `src/trm/data/custom/generator.py`:
a 30×30 maze carved by recursive backtracking, a start S and goal G, 1–4
mandatory checkpoints C, 1–5 reward tiles R (cost 0.5 to cross) and 1–5
penalty tiles N (cost 4). The label (`solve.py`) is the minimum-cost route
from S to G that visits every C: Dijkstra between key points, then exact
Held–Karp over checkpoint orders. Crossed R/N tiles are written `r`/`n`.
The token set `# SGoCRrNn` extends Maze-Hard's, so token ids 1–5 keep their
meaning. The training set has 5,000 mazes.

**Evaluation set.** A fixed 1,000-maze set (`scripts/build_maze_splits.py`):
the original 500 test mazes plus 500 new mazes from the same generator, none
of which appear in training. Used by E2, E6, E7.

**Metrics.**
- *Exact match*: the whole predicted grid equals the label (the model's
  built-in metric).
- *Checker verdict* (`src/trm/evaluation/maze_checker.py`, introduced in E5):
  each prediction is valid-and-shortest, valid-but-longer or broken, with
  reasons. A prediction is valid when every cell keeps its tile apart from
  path markers, S, G and every C are connected, and the cheapest
  S → checkpoints → G walk within the marked cells uses every marked cell.
  It is shortest when that walk's cost equals the optimum.
- *Reaches all checkpoints*: every C lies in the marked region connected to
  S. This is the routing measure (see M2).
- Proportions carry Wilson 95% confidence intervals.

**Compute.** Single GPU jobs on UNSW Katana (A100, L40S or H200 depending on
the scheduler); job scripts in `scripts/katana/`. Each fine-tune run freezes a
copy of the code it ran with into its checkpoint folder.

## E1 — Maze-Hard baseline reproduction

**Question.** Does the published Maze-Hard checkpoint reach its reported
accuracy when evaluated with this codebase?

**Why.** Every later experiment starts from this checkpoint and uses this
evaluation code. If the starting point or the evaluation pipeline were off,
nothing downstream could be interpreted. Confirming the published number
first separates "our setup is wrong" from "the transfer does not work".

**Setup.** `maze_hard_step_32550` on the 1,000 Maze-Hard test mazes, 16 ACT
steps, EMA weights (`scripts/katana/rescore_baseline.pbs`).

**Result.** 852/1,000 exact (85.2%, 95% CI 82.9–87.3%). The paper reports
85.3%; the independent alphaXiv reproduction reports 83.67% ± 2.28%. The
same 852 was obtained by a second script on different hardware (E3 control:
L40S vs. A100).

**Interpretation.** The checkpoint and the pipeline reproduce the published
result; later differences cannot be attributed to the starting point.

**Outputs.** `tab_baseline_outcomes`, `fig_baseline_outcomes`; raw data in
`results/maze_hard_baseline/`.

## A1 — What the two tasks actually require

**Question.** Which decisions does each task ask the model to make, and is
exact match a sound measure of success on each?

**Why.** Exact match is only a fair metric when each maze has a single
correct answer. The custom task was designed so that reward/penalty tiles and
checkpoint order would create cost trade-offs; whether the generated mazes
actually produce such trade-offs had not been checked.

**Method.** Graph analysis of the open cells of every evaluation maze
(`task_properties()` in `scripts/make_report.py`): cycle detection, re-solving
each custom maze with all tile costs set to 1, comparing each label with the
minimal subtree connecting S, G and every C, and counting distinct shortest
S–G routes in Maze-Hard by breadth-first path counting.

**Result.**

| | Custom eval set | Maze-Hard test |
|---|---|---|
| Mazes with cycles | 0 / 1,000 | 1,000 / 1,000 |
| Mazes with ≥ 2 checkpoints | 759 | — |
| Reward/penalty weights change the optimal route | 0 / 1,000 | — |
| Label equals the minimal subtree spanning S, G and all C | 1,000 / 1,000 | — |
| Distinct shortest routes | exactly 1 | min 96, median 3.8 million |

**Interpretation.**
- *Custom mazes have exactly one correct answer.* The generator carves
  perfect mazes (trees), in which the path between two cells is unique. The
  set of cells any valid route must mark is therefore the minimal subtree
  connecting S, G and the checkpoints, whatever order they are visited in. On
  this task exact match equals valid-and-shortest, and a valid-but-longer
  answer cannot exist.
- *Rewards and penalties never affect the route.* In all 1,000 mazes the
  optimal route is the same with and without tile costs; R/N tiles only
  change how a crossed tile is written (`r`/`n`). The task, as generated,
  tests multi-target routing (connecting up to five key points) and correct
  tile rendering, not cost trade-offs.
- *Maze-Hard is the opposite.* Every maze has loops and at least 96 equally
  short routes (median about 3.8 million). Exact match there asks the model
  to reproduce the dataset's particular choice among them, which is why E5 is
  needed.

**Implication for the thesis.** Claims about learning "objective-conditioned"
routing should be limited to checkpoint routing. Testing cost trade-offs needs
mazes with loops (for example, removing a fraction of walls after carving) —
a natural next experiment.

**Outputs.** `tab_task_properties`; macros `\CustomWeightsChangeRoute`,
`\HardShortestMin`, `\HardShortestMedianMillions`.

## E2 — First custom-maze run

**Question.** Can TRM learn the custom task with the first configuration
tried (July 2026)?

**Why.** This was the first attempt at the thesis task. It is reported
because its failure determined the next three experiments.

**Setup** (`config/resolved/maze_custom_first_run.yaml`). Batch size 1,
learning rate 2×10⁻⁵ (200 warm-up steps, then constant), weight decay 1.0,
50 epochs = 25,000 steps, which implies 500 training mazes. The config
records `load_checkpoint: null`: the run started from **random
initialisation**, not from the Maze-Hard checkpoint. (Loading that
checkpoint directly was impossible anyway, because the vocabulary had grown
from 6 to 11 tokens.)

**Result.** The original checkpoint sweep (`results/first_run/legacy_checkpoint_sweep.csv`;
its evaluation set was not recorded) shows 0% exact match at every saved
step from 5,000 to 25,000, with token accuracy around 80%. Re-scored on the
1,000-maze evaluation set, the final checkpoint gets 0/1,000 exact; every
prediction is broken. 99.2% fail to connect at least one checkpoint to S, and
95.9% do not join S to G.

**Interpretation.** The run learned no route structure. Its 80% token
accuracy comes from copying walls and empty cells, which is why token
accuracy is not reported as a success measure elsewhere. Two causes are
confounded: no pretraining and a batch size of 1. The next step was to start
from the pretrained checkpoint, which first required a vocabulary expansion
(E3).

**Outputs.** `tab_first_run`; raw data in `results/first_run/`.

## E3 — Vocabulary expansion check

**Question.** After the embedding and output layers are expanded from 6 to
11 tokens, does the pretrained model still solve Maze-Hard?

**Why.** Fine-tuning from the pretrained checkpoint needs five new tile
tokens. If the expansion itself damaged the model (for example, by moving
token ids), a later fine-tuning failure could not be told apart from a
broken starting point. This test isolates the expansion, with no training
involved.

**Method.** `scripts/expand_checkpoint_vocab.py` copies every weight of
identical shape; for the two vocabulary-sized tensors (token embedding and
output head) it copies the 6 original rows and leaves the 5 new rows at
fresh random initialisation. It asserts that the new token set begins with
the old one, so ids 1–5 keep their meaning. Both checkpoints are then
evaluated on Maze-Hard (`scripts/katana/transplant_check.pbs`).

**Result.**

| Checkpoint | Exact match | Token accuracy | Loss |
|---|---|---|---|
| Original (6 tokens) | 85.2% | 99.52% | 0.033 |
| Expanded (11 tokens) | 85.2% | 99.52% | 0.135 |

**Interpretation.** The expansion leaves every prediction unchanged. The loss
rises because the five untrained output rows take some probability mass, but
never enough to change the most likely token. The expanded checkpoint is a
sound starting point for E4, E6 and E7.

**Outputs.** `tab_transplant`; raw data in `results/diagnostics/`.

## E4 — Fine-tuning the expanded checkpoint (v4)

**Question.** Starting from the expanded checkpoint, does fine-tuning learn
the custom task?

**Why.** E3 established a sound starting point, and E2 suggested that
training from scratch was not viable at that scale.

**Setup.** Only the evaluation history survives
(`results/v4_finetune/eval_metrics.csv`); the run's config and weights were
not kept. The configuration below is *inferred* from that history (see M3):
500 training mazes, 100 test mazes, batch size 16, evaluation every 10 epochs
(312 steps), 120 epochs (3,744 steps) recorded. The learning rate is not
recorded. One seed.

**Result.**

- Exact match rises from 3% (step 312) to a best of 97% at step 3,432
  (Wilson 95% CI 91.5–99.0% on 100 mazes), ending at 95% at step 3,744.
- A single connected S–G route (corrected, see M1) rises from 19% to 98%.
- During training it leads exact match by up to 16 points (step 2,184).

**Interpretation.** Starting from the pretrained checkpoint, the task is
learned in about 3,000 steps where training from scratch (E2) learned nothing.
Because custom mazes have one valid answer (A1), the gap between "connected"
and "exact" counts connected outputs that are still wrong in detail, for
example a checkpoint left off the route or a mis-rendered tile. It is not a
count of alternative correct routes.

**Caveats.**
- One seed, 100 test mazes: the confidence interval spans about 8 points.
- The 100 test mazes are not in the repository, and the learning rate is
  unknown.
- The Thesis B claim that "routing is solved by step 1,248, while exact match
  is 32%" rests on a metric that does not measure routing (M2) and is
  withdrawn.

E6 is the replication designed to address these.

**Outputs.** `tab_v4_trajectory`, `fig_v4_curves`.

## E5 — Route checker and Maze-Hard re-score

**Question.** When the baseline is wrong by exact match, is it actually
wrong?

**Why.** Exact match treats three different things as one failure: an
equally short route that differs from the label, a valid but longer route,
and an output that is not a route at all. A1 shows the first is unavoidable
on Maze-Hard. To compare models fairly, and to see what kind of errors
fine-tuning removes, the evaluation needs to separate them.

**Method.** The checker described in Shared setup. Treating a route as a
walk rather than a simple path matters for the custom task: a checkpoint in a
dead end is reached by entering and leaving the same corridor, so correct
labels contain spurs a simple-path test would reject. Validation: every one
of the 1,000 Maze-Hard labels and 6,000 custom labels (all 5,000 training
and 1,000 evaluation mazes) is classified valid-and-shortest. Unit tests in `tests/test_maze_checker.py`
cover detours, loops, gaps, stray marks, walls, wrong markers and
penalty-tile trade-offs.

**Result** (the 148 baseline failures from E1).

| Verdict | Mazes | Share of failures |
|---|---|---|
| Valid, shortest, ≠ label | 64 | 43.2% |
| Valid, longer | 76 | 51.4% |
| Broken | 8 | 5.4% |

- Of the longer routes, 59 are exactly 2 steps too long, which is the cost of
  going around a single wall block the wrong way.
- Of the broken outputs, 6 erase the goal tile and 2 leave S and G
  disconnected.
- Valid-and-shortest accuracy is 91.6% (95% CI 89.7–93.2%), against 85.2%
  exact.

**Interpretation.**
- Exact match understates the baseline by 6.4 points.
- The model's real error is small detours, not broken output: fewer than 1%
  of outputs fail to be a route at all.
- On custom mazes the checker's value is diagnostic rather than corrective:
  exact match and valid-and-shortest coincide there (A1), but the reasons
  attached to broken outputs show *how* a model fails.

**Outputs.** `tab_baseline_outcomes`, `tab_baseline_failure_detail`,
`fig_baseline_outcomes`.

## E6 — Seed replication of v4 (running)

**Question.** Is v4's result reproducible, and how much does it vary with
the random seed?

**Why.** E4 is a single run on 100 test mazes with an unrecorded learning
rate. A thesis claim needs at least a second seed and a larger, fixed
evaluation set.

**Setup.** 500 training mazes (the first 500 of the 5,000-maze training set;
mazes are generated independently, so a prefix is a random sample). Batch
size 16, which gives the same 312 steps per 10 epochs as v4. 150 epochs
(4,687 steps). Learning rate 10⁻⁴ (200 warm-up steps, then constant), weight
decay 1.0, EMA 0.999, starting from the expanded checkpoint. Seeds 0 and 1.
Evaluation every 100 steps on the 1,000-maze set; checkpoints every 250
steps. Runs `ft_custom_n500_lr1e-4_b16_s{0,1}`.

**Hypothesis.** If v4 was representative, both seeds reach ≥ 90% exact match
within about 3,000–4,000 steps, and the seeds end within a few points of each
other. Otherwise, v4 was either a favourable seed or relied on a learning rate
different from 10⁻⁴; these runs cannot tell those apart.

**Result.** Pending.

**Outputs (when finished).** `tab_finetune_runs`, `fig_finetune_curves`,
`fig_finetune_final_verdicts`; macros `\FtReplica...`.

## E7 — Ten times more training data (running)

**Question.** Does training on 5,000 instead of 500 mazes change accuracy or
learning speed?

**Why.** A 500-maze training set may limit generalisation to unseen mazes.
This run uses all 5,000 generated training mazes.

**Setup.** As E6 but on all 5,000 mazes with batch size 160. Steps per epoch,
total steps and learning rate are the same as E6, so each update sees 10×
more examples. Seeds 0 and 1. Runs `ft_custom_lr1e-4_b160_s{0,1}`.

**Hypothesis.** If training-set diversity limits generalisation, E7 ends
higher than E6 or reaches 90% sooner.

**Caveat.** Data size and batch size change together at a fixed learning
rate, so a difference cannot be attributed to data alone. Separating them
would need a 5,000-maze run at batch size 16 (about 10× more steps).

**Result.** Pending.

## Measurement corrections

**M1 — Padding rows counted as mazes (fixed).** The evaluator's structural
metrics (`path/*`) decided which rows were padding by checking
`labels != 0`. But the data loader rewrites label padding to −100, so padding
rows were scored as failed mazes. Exact match was unaffected, because it is
computed separately.

- *Effect on v4.* 100 real mazes were padded to 112 rows. For metrics on
  which padding scores 0 (connected, has_endpoints), the corrected value is
  the reported value × 112/100.
- *Check.* The correction is confirmed wherever exact match ≥ 89%: there, the
  uncorrected values would put connectivity below exact match, which is
  impossible. For earlier evaluations it is assumed.
- *Not recoverable.* `largest_component` and `n_components` cannot be
  corrected and are no longer reported.

The fix filters on the input grid instead.

**M2 — "All checkpoints visited" did not measure routing (replaced).**
`path/all_checkpoints` counts a checkpoint as visited when the output cell
reads `C`. A checkpoint tile always reads `C`, so copying the input scores
100%. On the 1,000-maze set, copying the input scores 100% on that metric
and 0.1% on the replacement `path/reaches_all_checkpoints`. The two agree on
correct labels (both 100%). The old metric remains in old logs for
comparability, documented as "C tiles kept".

**M3 — v4's configuration was inferred, not recorded.**

- *Test set size.* Every v4 exact-match value is a multiple of 0.01 (12 of
  12), so the test set had 100 mazes.
- *Padded rows.* Every structural value is a multiple of 1/112, and
  "exactly one start and goal" levels off at exactly 100/112, so those 100
  mazes were padded to 112 rows.
- *Batch size and training size.* The batch size b must satisfy
  ⌈100/b⌉·b = 112 (b ∈ {14, 16, 28, 56, 112}). The training set N must give
  312 steps per 10 epochs. Of these combinations, only b = 16 with N = 500
  matches the generator's defaults (500 train / 100 test).

E2's config independently confirms 500 training mazes at that time. The
learning rate cannot be recovered.

## Threats to validity

- **In-distribution evaluation only.** All custom evaluation mazes come from
  the training generator. Nothing here measures transfer to different maze
  sizes, densities or tile counts.
- **Task simplicity (A1).** Results on custom mazes speak to multi-target
  routing and tile rendering, not cost-sensitive planning.
- **Few seeds.** Two seeds per configuration give a range, not a variance
  estimate.
- **Unrecovered v4 details.** v4's learning rate and test mazes are unknown,
  so E6 replicates its data size and batch size, not the run itself.
- **Confounded scaling (E7).** Data size and batch size change together.
